本报告基于 APK 原始字节、DEX 指令和 ARM64 反汇编。附录收录 30 个受保护方法的定位信息和 571 个指令位置的解码记录。

## 1. 保护落在什么地方

主包根目录的 57 个 DEX 全部通过长度、SHA-1 和 Adler-32 检查，共 468,906,196 字节、563,104 条类定义。其中 411,863 条位于 `LX/` 描述符前缀下，名称混淆范围很广。宿主应用与组件工厂均在 `classes38.dex` 可读。能够完整配对的虚拟化保护集中在 `cn.wh.auth`、其子包以及 `cn.wh.authapi.BuildConfig`。这 30 个方法分布在 11 个类中，Java 层 16 个在 `classes16.dex`，14 个在 `classes55.dex`。

| 样本项 | 值 |
| --- | --- |
| APK 文件名 | aweme_douyinweb1_64_v5072_410101_6549_1794384883.apk |
| APK 字节数 | 365,684,313 |
| APK SHA-256 | `b45ace86aa97a696cbf2767a0a10f96d37c88e814a2ee19269d84f600ad9b1e3` |
| 重点原生库 | `lib/arm64-v8a/libdexvmp.so`，492,024 字节 |
| 原生库 SHA-256 | `0c8a58be920c8afb336f54b84cfbb23cb932086d6bee482a383e402c4c1ca29a` |

### 宿主的启动代码仍然能读到什么

Manifest 指定的 Application 是 `com.ss.android.ugc.aweme.app.host.AwemeHostApplication`。其 `attachBaseContext()` 调用场景跟踪、加载 Jato 原生库，并访问宿主服务。其 `onCreate()` 能读到冷启动日志、进程判断和预装逻辑。组件工厂 `AwemeAppComponentFactory` 的辅助方法调用字节 SafeMode 的 `instantiateClassLoader` 和 `instantiateApplication`。这些都能在 DEX 指令中直接定位。就本次检查的启动链，没有发现统一解密全部宿主 DEX 的证据。

## 2. 从 Java 调用点追到 ARM64

以 `WAuth.getAuthResult(OnCallBack)` 为例。它在 `classes16.dex` 中创建对象数组，依次放入当前实例、回调对象、装箱后的整数 2，再调用 `JniLib1755042153.cV`。与原始包装指令等价的伪代码如下。

```java
JniLib1755042153.cV(new Object[] {this, callback, Integer.valueOf(2)});
```

桥接类全名为 `com.fort.andJni.JniLib1755042153`，在 `classes55.dex` 中。类初始化以 `dexvmp` 为库名调用宿主加载函数。库内 `0x6e090` 恰好存放同一个类名，包含大小写一致的 `andJni` 和数字后缀。

| ARM64 ELF 虚拟地址 | 可观察行为 |
| --- | --- |
| `0x8e5c` | `JNI_OnLoad` 获取 JNI 1.4 环境，调用初始化函数，并把桥接类名传入注册路径 |
| `0xeadc` | 构造由名称、JNI 签名和 ARM64 函数地址组成的十项注册表 |
| `0xed6c–0xed80` | 从 JNIEnv 表偏移 1720 取函数指针，传入数量 10 后间接调用。64 位下索引为 215，对应 `RegisterNatives` |
| `0x1606c` / `0x160c0` / `0x1619c` | 分别是本次业务调用命中的 `cV`（void）、`cL`（对象）和 `cZ`（boolean）入口 |
| `0x16220` | 三个入口汇合于此。先取数组长度，再读下标 `length - 1` 的元素，调用整数取值路径，使用分发编号选择方法记录 |

十个入口分别对应 V、I、L、S、C、B、J、Z、F、D。扫描得到的 30 个直接业务调用中，20 个走 `cV`，8 个走 `cL`，2 个走 `cZ`。Java 类还有 native 方法 `a`，上述十项注册表的计数仅针对这组类型化分发入口。

## 3. 方法体在 SO 文件里的存放方式

下表地址均为 **SO 文件偏移**。方法编号直接取自外层 DEX 最后一个数组元素，随后与 SO 内的方法编号、短签名交叉核对，30 条全部匹配。

| 文件偏移 | 长度或数量 | 内容 |
| --- | --- | --- |
| `0x74008` | 4,490 字节 | 以原始 LZ4 块解压后得到 10,465 字节，依次解析出 5 个 MessagePack 数组 |
| `0x76928` | 30 条方法记录 | 首个值为 30。每条依次给出编号、二进制方法体、4 个整数和短签名 |
| `0x775e5` | 30 组位置表 | 各组包含编号、位置数、最大位置和若干位置/掩码对。共 571 个已标记位置 |

第一块中的两个字符串数组分别有 256 和 279 项，另有 58 个类型索引、102 个字段索引值和 500 个方法索引值。按三元组得到 34 条字段引用，按四元组得到 125 条方法引用。例如引用方法 25 解为 `android/content/pm/PackageManager.getPackageInfo(String,int)`。这些池使用自身的索引，解析引用时需要选择对应的池。

方法记录保留了与 DEX `code_item` 相符的寄存器数、入参数、出参数、异常处理项数和 16 位指令单元数。对位置表中给出的位置，将该位置首个字节与对应掩码异或，可以得到跨方法稳定的内部操作码。本样本这 571 处共出现 32 种内部操作码。下面这个两指令方法可独立复核该过程。

### 最小复核样例：方法 8

`WAuthService.getVersion()` 的二进制方法体起于 `0x77021`。跳过 16 字节头，指令区是 `a5 00 0a 00 a2 00`。位置 0 和 2 的掩码分别是 `bd` 和 `a7`，位置单位为 16 位。首条得到 `a5 XOR bd = 18`，取字符串池第 10 项；第二条得到 `a2 XOR a7 = 05`，返回对象。由此还原：

```java
return "1.5.4";
```

这是认证组件的方法返回值。抖音宿主版本来自 Manifest，为 41.1.0。

## 4. 被保护的认证流程

### 入参和目标组件

方法 5 `WAuth.init()` 读取 `WParams`。代码含返回“参数格式异常”的分支，结果码为 `C0401001`。对于非空的 `extras`，可见 `startsWith("{")`、`endsWith("}")` 检查。这段指令只证明检查了首尾字符，无法由此推出它验证了完整 JSON 语法。

随后构造显式 `ComponentName`，包名为 `cn.cyberIdentity.certification`，Activity 为 `cn.wh.project.view.v.authorization.WAuthActivity`。方法向 Intent 写入 `extras`、`orgID`、`appID`、`bizSeq`、`type`。宿主 Manifest 也声明了该目标包。

### 调用前的目标检查

方法 2 `WAuth.getAuthResult()` 保存回调对象，读取已有结果状态，构造 Intent，设置 `packageName` 附加值，调用 `PackageManager.resolveActivity()`。无法解析目标的分支使用 `C0412002` 和“国家网络身份认证APP尚未安装”。同一方法的异常处理路径也使用这组值，所以看到该提示并不能单独确定设备上的安装状态。

在继续启动前，方法 2 还调用 `CheckInstall.verifyAppSignature(context, "cn.cyberIdentity.certification")`。这个校验函数自身可在 `classes55.dex` 直接检查。它取目标包首个签名的字节，计算 SHA-1，使用 `%02x` 转十六进制后与预设值进行忽略大小写的比较。样本内常量为 `76db302749c810ef6c1788295259a43da8ecaac6`。该值用于检查外部目标包。签名校验异常的分支设置 `C0412009` 和“签名校验异常”，正常后续路径调用 `ResultRequestService.startForResult()`。

### 结果如何返回

方法 25 将启动工作交给 `Activity.runOnUiThread()`。方法 27/28 用标签 `on_wh_local_result_dispatcher` 查找或创建结果分发 Fragment。方法 23 调用 `SparseArray.put()` 保存回调，再调用 `startActivityForResult()`。方法 21 的返回路径则读取并移除回调。

在方法 0 `WAuth$1.onActivityResult()` 中，可见从返回的 Intent 读取 `resultCode`、`resultDesc`、`idCardAuthData`、`certPwdData`、`verifyData`、`extrasData`，分别写入结果对象再回调。代码还包含“用户已取消”（`C0412003`）和“数据处理异常”（`C0405001`）路径。这些是静态可达路径和字段名，本次没有采集任何真实用户的认证数据。

## 5. 容易混淆的其他组件及结论边界

- `libmetasec_ml.so` 为另一个 ELF，DEX 内的 `com.bytedance.mobsec.metasec.ml.MSB` 及 `TTnetSoPreloadTask` 可见 `metasec_ml` 引用。本次还原的 30 个方法与 `libdexvmp.so` 的 30 条记录已经单独配对，没有依据把它们算给 MetaSec。
- 对 `lib/arm64-v8a/` 下的 268 个 `.so` 文件名逐一读取魔数，267 个为 ELF，另一个 `libsm_impl.so` 直接以 `dex\n035\0` 开头，含 `com.bytedance.safemode` 类。`libsm_loader.so` 中也出现 `SafeModeV4`。因此“DEX 藏在 .so 后缀下”和“认证方法虚拟化”在该样本中分别有不同的证据。
- 结论覆盖主包 57 个顶层 DEX 对指定桥接类的直接调用，以及与它们配对的 ARM64 数据。未对所有插件归档和其余原生库作穷尽式反编译，未在 Android 真机触发认证流程。现有证据足以识别该模块的 VM 保护机制，无法独立确认商业加固厂商、运行时反调试策略或全部风控行为。
